# K-Veritas Go 用签名 PDF 证明代码跑过，但信任根仍是软肋

> K-Veritas Go 通过签名 PDF 和硬件遥测为计算过程提供可验证出处，但 HN 评论者质疑其防伪能力，核心矛盾在于信任根是否真的不可伪造。

## 一句话看懂

K-Veritas Go 试图解决一个真实痛点：当审阅者无法或不愿重跑代码时，如何证明报告中的结果确实由特定代码在特定硬件上产生。它给出的答案是“执行见证”——在计算过程中采集遥测数据，生成密码学签名的 PDF。但 HN 上的质疑直指要害：如果攻击者控制运行环境，签名只能证明作者签署了报告，不能证明报告内容真实。这个工具的价值和边界，都藏在信任根的设计里。

## 核心体验

K-Veritas Go 的使用流程围绕几个命令展开：init 初始化项目，run 执行计算并采集遥测，seal 生成签名 PDF 报告，verify 验证报告完整性。用户可以在代码中通过 stdout 打印协议行来记录指标、阶段、声明、模型卡等，这些内容会被纳入报告。后台采样器以约 10Hz 频率记录进程级遥测，包括 CPU、内存、上下文切换、页错误和 GPU 利用率。

报告的核心是 HMCA（执行连贯性）评分。它不看报告结果，只看多个遥测通道是否像同一进程的影子一样共同波动，给出 PASS、WARN、FAIL 或 N/A 的判定。另一个关键机制是计算成本证明：检查声明的 FLOPs 是否超出硬件物理极限，并设置时间、能量和内存的边界。报告支持三种披露级别（redacted、names、open），默认 redacted，但完整性始终被提交。选择性披露证明允许只揭示某个文件或记录，而不暴露其他内容。

从产品角度看，K-Veritas Go 试图把“代码确实跑过”变成一种可验证的声明，而不是依赖审阅者重跑。它跨平台，但文件/子进程活动映射和每进程硬件归因仅限 Linux，其他平台回退到系统级读数。

## 为什么有效

K-Veritas Go 的有效性来自两个设计选择。第一，HMCA 是度量盲的：它不关心报告声称的结果是什么，只关心遥测数据是否呈现出一致的行为模式。真实运行会自然产生 CPU、内存和 I/O 之间的相关性，而伪造数据很难在所有维度上保持连贯。这增加了伪造的难度，因为攻击者不仅要伪造结果，还要伪造一组在多个维度上相互吻合的遥测数据。

第二，计算成本证明利用硬件物理极限作为不可逾越的约束。任何声称超过峰值 FLOPs 或能量消耗的计算都会被标记为 FABRICATION-IMPOSSIBLE。物理定律无法被篡改，这比单纯依赖软件日志更难以绕过。签名和 Merkle 树保证了报告内容不可篡改，而选择性披露则允许在保护隐私的同时提供可验证的证据。对于 AI 产品经理而言，这意味着可以低成本地为模型训练或推理过程附加可信的出处证明，而无需让审阅者重新运行昂贵的计算。

## 问题与边界

HN 评论者的质疑切中了信任根问题：如果攻击者能控制运行环境，他们可能伪造遥测数据或签名，除非在安全 enclave 中运行。K-Veritas Go 的签名只能证明作者签署了报告，不能证明报告内容真实。这是所有软件级证明工具的共同局限。

HMCA 本身也有误判风险。轻量运行可能因遥测数据不足而得到 N/A，而精心构造的伪造可能通过连贯性检查。平台限制也很明显：文件/子进程活动映射和每进程硬件归因仅限 Linux，其他平台回退到系统级读数，降低了精确性。性能开销未明确量化，后台采样可能对计算密集型任务产生额外负载。多进程或分布式计算支持不明确，可能无法覆盖复杂工作流。

## 我的判断

K-Veritas Go 代表了一类新兴的“可验证计算”工具，它试图在软件层面解决信任问题，但根本挑战在于信任根。如果用户完全控制运行环境，任何软件级证明都可能被绕过。除非结合硬件信任根（如 TPM、SGX）或第三方见证，否则该工具更适合作为威慑或低风险场景的辅助证据，而非绝对证明。

对于 AI 产品经理，其价值在于提供了一种轻量级的出处记录和审计线索，尤其在需要向非技术利益相关者展示模型训练过程时。但产品设计上应明确其安全边界，避免过度承诺“防篡改”。

## 可迁移的方法

### 1. 物理边界证明

利用硬件物理极限（如峰值 FLOPs、能量消耗）作为不可逾越的约束，检查声明是否可能由给定硬件产生。这比单纯依赖软件日志更难以伪造，因为物理定律无法被篡改。

**适用场景：** 适用于需要验证计算资源声明（如训练成本、推理延迟）的场景，尤其是当审阅者无法直接访问运行环境时。

### 2. 度量盲的连贯性检查

不检查报告结果本身，而是分析多个遥测通道是否呈现出一致的行为模式（如 CPU 和内存使用同时上升）。真实运行会自然产生这种相关性，而伪造数据很难在所有维度上保持连贯。

**适用场景：** 适用于需要检测伪造或重放攻击的场景，例如验证实验是否真的执行过，或监控 AI 模型推理是否在声称的硬件上运行。

## 产品启示

AI 产品经理在设计可验证或审计功能时，应明确信任根的位置：软件级证明只能提供辅助证据，真正的信任需要硬件信任根或第三方见证。同时，度量盲的连贯性检查是一种值得借鉴的防伪思路，它不依赖结果正确性，而是关注过程一致性。
