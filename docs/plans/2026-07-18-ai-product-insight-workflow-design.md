# AI 产品洞察工作流设计

## 目标

为个人作品集网站建立一条可重复运行的内容生产链路：每两周自动发现候选产品，也允许手动指定产品；系统基于公开证据生成约 5 分钟的中文洞察草稿，经人工审核后才进入网站。

## 内容定位

- 70% 前沿 AI 产品深度拆解，30% 新奇产品观察。
- 每篇约 900-1200 个中文字符，强调第一人称产品判断。
- 固定结构：一句话看懂、核心体验、为什么有效、问题与边界、我的判断、可迁移的方法、信息来源。
- 自动化只负责候选筛选、证据整理和草稿生成，不自动发布。

## 架构

工作流采用顺序式多 Agent，而非让多个 Agent 自由对话：

1. Discovery Agent 从 RSS、Hacker News 等公开入口抓取候选，合并手动输入并去重。
2. Scout Agent 使用规则与 DeepSeek 对候选进行相关性、新颖性、产品价值和证据完整度评分。
3. Research Agent 抓取候选页面，形成带来源 URL 的证据包，明确事实、推断和体验缺口。
4. Insight Agent 将证据提炼为产品机制、有效原因、限制与可迁移方法。
5. Editor Agent 生成个人化但克制的中文文章草稿，并通过 Pydantic 数据模型校验。
6. Renderer 输出 Markdown、JSON 和可嵌入现有网站的 HTML 卡片。

所有步骤输出可序列化的中间文件，失败时可从最近阶段重跑。DeepSeek 通过兼容 OpenAI 的 `/chat/completions` 接口调用，并要求 JSON 输出；API Key 只从环境变量读取。

## 触发与审核

- 本地：命令行支持 `scheduled`、`manual` 和 `offline-demo` 三种模式。
- GitHub：`schedule` 每两周运行，`workflow_dispatch` 接收产品名称和 URL。
- 线上工作流创建内容分支和 Draft Pull Request。用户审核并合并后，才由现有 GitHub Pages 发布流程更新网站。
- 若仓库未允许 Actions 创建 PR，工作流保留草稿 Artifact 并给出设置提示。

## 错误处理

- 单个信息源失败不会中断其余来源；错误写入运行报告。
- URL 归一化与内容指纹用于去重，历史候选写入状态文件。
- 网络请求具备超时、有限重试和明确 User-Agent。
- LLM 返回值先做 JSON 解析，再做 Pydantic 校验；失败时最多进行一次修复请求。
- 没有足够证据时只输出研究不足状态，不编造文章。

## 验收标准

- 无 API Key、无网络时可使用固定样例完整跑通。
- 自动发现与手动输入都能产出同一数据契约。
- 不满足证据阈值的候选不会进入写作阶段。
- 任何输出都包含来源 URL、审核状态和生成时间。
- GitHub Actions 文件不包含明文密钥，且默认只创建待审核草稿。
