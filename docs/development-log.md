# AI 产品洞察工作流：开发与问题记录

最后更新：2026-07-20

## 当前能力

- `scheduled`：从公开来源发现候选产品，评分后生成一篇草稿。
- `manual`：指定一个产品、一个主要页面和个人观察，生成单产品洞察。
- `compare`：指定 2–6 个产品及个人体验，分别研究后生成一篇对比文章。
- 编辑上下文：自动加载文章结构、语言规范、评分标准和 `examples/gold/` 下全部人工确认的金标准输入/输出。
- 一次性追问：本地 `compare` 在研究完成后最多追问 3 个问题，只进行一轮；问答写入运行检查点。
- 输出：JSON、Markdown、首页卡片 HTML，状态默认为 `draft`。
- `publish`：从 Markdown 生成网站文章预览；输入明确确认词后标记 `approved`、更新静态网站、提交并推送 GitHub。

## 主要演进

### 2026-07-18：MVP

- 使用轻量 Python 编排实现 Scout、Research、Insight、Editor 四个顺序 Agent。
- 接入 DeepSeek JSON 模式，保留离线演示和人工审核。
- 输出结构化 JSON、Markdown 和卡片 HTML。
- 暂不引入 CrewAI，减少依赖并保持各阶段可测试。

### 2026-07-19：真实运行兼容

- 增加 DeepSeek 输出边界规范化，兼容模型返回的常见字段别名和结构变化。
- 将第一篇人工编辑文章保存为编辑金标准，增加七段式结构、个人表达、证据边界和评分规则。
- Insight 与 Editor 在写作时自动加载编辑上下文，但不得复制范例中的产品事实和措辞。

### 2026-07-20：对比、追问与发布

- 新增多产品 `compare` 模式，跳过无意义的发现和候选评分，逐个研究指定对象后统一成稿。
- 新增一次性编辑追问，补充具体时刻、前后差异和个人判断。
- 新增 GitHub Pages 静态发布器，适配现有纯 HTML/CSS/JS 网站和 `.nojekyll` 配置。
- 发布前先生成不修改网站的预览；确认后只提交本次生成的文章、样式、清单和首页卡片。
- 根据个人网站的真实协作记录重写四个 AI 工具对比文章，并保存为第二组金标准。
- 编辑上下文由固定加载第一篇范例改为自动加载全部成对范例；缺少对应输出文件时立即报错。

## 已遇到并修复的问题

| 问题 | 表现 | 原因 | 修复 |
|---|---|---|---|
| Windows Python 启动器缺失 | `py is not recognized` | 系统没有 `py.exe` | 改用已安装 Python 或虚拟环境中的 `python.exe` |
| Scout 评分结构不一致 | Pydantic 校验失败 | DeepSeek 将评分字段放在 `candidate_id` 同级 | 在模型边界把平铺评分归一化为 `score` 对象 |
| Research 质量字段别名 | `quality` 缺失、`evidence_quality` 多余 | 模型使用了提示词之外的别名 | 进入严格模型前统一为 `quality` |
| Insight 字段布局变化 | `one_line` 等缺失，出现 `explanation`、`judgment` | 模型返回另一套语义相近字段 | 增加别名映射、字符串列表转换和方法结构兼容 |
| Editor 标签过多 | `tags` 返回 5 项 | JSON 模式不保证数量约束 | 去重并截取前 4 项 |
| 方法数量约束冲突 | 第一篇金标准有 4 条方法，但旧模型最多 2 条 | 上下游 Schema 未统一 | 文章允许 2–4 条；单产品洞察最多 2 条，对比洞察最多 4 条 |
| 对比研究全部证据不足 | 四个产品 `selected_count` 为 0 | 全局要求 2 条证据，但对比参数每个产品只提供 1 个 URL | 对比研究允许 1 条公开资料；资料失败时保留个人体验但禁止扩写为事实 |
| 对比洞察返回 3 条方法失败 | `patterns` 超过 2 项 | Compare 提示与 ProductInsight 上限冲突 | 对比模式允许并规范化到最多 4 条 |
| 摘要超过 180 字 | Editor 最后阶段校验失败 | DeepSeek 忽略字符上限 | 所有文章字段和方法字段增加优先按完整句收束的长度容错 |
| Wikipedia 被标成官方来源 | 来源列表显示 `Wikipedia（official）` | 抓取器把所有直接页面默认设为 `official` | Wikipedia、Reddit、Hacker News 域名改标 `community` |
| 网站样式入口发生变化 | 文章预览器找不到 `style.css` | 个人网站已拆分为 `home.css` 与 `detail.css` | 待发布前调整预览器的样式发现与复制逻辑；不影响 Markdown 和金标准生成 |
| Hacker News SSL EOF | 运行报告出现抓取错误 | 外部接口连接异常 | 保持为非阻断发现错误，不影响已有候选继续运行 |

## 仍需注意

- 当前每个对比对象只接受一个主要 URL，尚未支持一个产品配置多个来源。
- 失败后尚不支持从已有 Research/Insight 检查点恢复，重新运行会再次产生模型调用。
- 来源类型目前使用小型域名规则，未来可将来源类型作为输入字段显式配置。
- 本机命令行暂未发现 Git 可执行文件；自动推送前需要安装 Git 或 GitHub Desktop，并确保 Git 可被程序找到。
- GitHub Pages 发布命令尚未对线上仓库执行真实推送；必须先用本地临时站点测试并人工确认。
- 自动生成内容仍然是草稿。事实、引用、第一人称经历和表达强度必须人工审核。

## 验证原则

- 每个真实报错先写回归测试，再修改实现。
- 单产品和对比模式分别保留数量约束，避免修复一个模式时改变另一个模式。
- 发布器在确认前只写预览目录，不修改网站仓库。
- Git 提交使用明确文件列表，避免把网站目录中其他修改带入发布提交。

## 2026-08-05：GitHub 每周自动草稿

- GitHub Actions 调整为每周一北京时间 09:20 自动生成 Draft Pull Request。
- 模型按阶段路由：Scout/Research 使用 DeepSeek V4 Flash，Insight/Editor 使用 DeepSeek V4 Pro。
- 首次推送排除虚拟环境、历史运行日志、自动草稿、预览、构建缓存与压缩包。
- 首次云端实跑虽然显示成功，但首选产品 Finyuus 的证据不足，未生成 Markdown，仍创建了仅含中间数据的 Draft PR。修复后 Scout 会保留最多 3 个有序候选，Scheduled 模式遇到证据不足时继续尝试下一项，并在第一篇成功草稿后停止。
- CLI 现在只有在实际产生输出时才返回成功；GitHub Actions 即使失败也会保留运行 Artifact，但不会再为无草稿运行创建“假成功”PR。

## 2026-08-09：社交改写与人工截图节点

- 在文章 Editor 之后新增下游 Social Repurpose Agent，同步生成一条不超过 280 字符的英文 X 草稿、中文小红书文案、4–8 页轮播结构和截图清单。
- 截图清单明确固定文件名、截取范围、用途、是否必需，以及图片来自个人项目还是讨论对象产品。
- Draft PR 新增 `inputs/assets/<slug>/` 人工上传区；真实截图提交到草稿分支后，第二个 GitHub Actions 工作流自动续跑，不需要重新生成文章。
- 新增蓝白视觉模板渲染器，生成 1600×900 的 X 配图和 1080×1440 的小红书轮播 PNG；截图仍是主体，模板只负责统一包装。
- 根据人工社交内容复核补充可执行的社交金标准：X 正文用 2–4 个短段落换行，且总长度不超过 280 字符；小红书正文约 300–500 字，保留具体经历、真实摩擦和判断过程；完整体验文章优先生成 6–8 页轮播，截图页说明证据含义，观点页保留足够推理密度。
- Social Repurpose Agent 现在会读取 `examples/gold/social-style.json`，避免社交规范只停留在单次人工修改；截图页模板同步扩大文字区域，内容放不下时优先调整排版，而不是删薄文案。
- 截图缺失、图片损坏或字体不可用都会给出明确错误；配图仍需人工检查隐私、裁切和观点对应关系，系统不会自动发布。
